## Takeaways

- The original primitive failure had several layers:
  - harness/linkage problems
  - codegen problems
  - transform encode level propagation problems
  - remaining true runtime scaling problems
- The transform encode level issue is fixed; it is no longer the main blocker.
- The current primitive shared-lib/bootstrap runtime still fails after codegen succeeds.
- The remaining failure moved from:
  - `invalid scaling factor for encode` caused by transform encodes at level `0`
  to:
  - a deeper scaling problem likely tied to later plaintext/scalar operations or overall scale-growth management.
- The next concrete debugging step is to inspect all remaining generated `Encode_double_mask(...)` / scalar encode sites and match their level/scale behavior against rtlib EvalMod semantics.
- The remaining high-value gap is now semantic rather than scaling-infrastructure:
  - the primitive mode now intentionally gets rtlib-identical semantics by composing the runtime stage ops directly
  - the next major question is performance / completion of the resnet20 generated-bootstrap integration rather than correctness on the bootstrap example
- Important correction:
  - lowering the primitive/bootstrap DSL path to `CKKS.bootstrap` / `Eval_bootstrap_ciph(...)` is absolute cheating for this project goal
  - even if tests or resnet outputs match, that state must not be treated as a valid decomposition-based DSL implementation
  - the required invariant is:
    - `ACE_BOOTSTRAP_IMPL=primitive` must not contain `CKKS.bootstrap` in raw AIR
    - final generated C for the decomposition path must not just call `Eval_bootstrap_ciph(...)`
  - current source has the shortcut removed again, but the regenerated raw AIR/C still need to be checked and fixed until this invariant holds
- Directly probing the output ciphertext before decode showed the primitive result can have:
  - low remaining level
  - extremely large `sf_degree`
  which is consistent with missing rescale / level-alignment semantics versus rtlib.
- Current refined understanding:
  - the major remaining resnet integration issue was not just “too many/few rescales” globally
  - a large part of the level mismatch came from primitive collapsed-FFT plaintexts being encoded at the wrong levels relative to rtlib `Rotate_precomp(...)`
  - after fixing those stage plaintext levels and switching the primitive body to raise to the full tower count, the live resnet bootstrap calls satisfy the requested target levels across the successful one-image run
  - the old early-call runtime rescale crash is fixed
  - remaining work is performance optimization and then stronger baseline-vs-DSL output comparison, not basic one-image resnet completion

## Lessons learned

- When debugging primitive bootstrap, separate these questions:
  1. does it trace?
  2. does it codegen?
  3. do explicit encode levels survive to final C?
  4. does the runtime return a decodable ciphertext?
- Inspect all three layers together:
  - raw AIR
  - post-`ckks_driver` AIR
  - generated C
- For primitive bootstrap, the strongest current suspicion is not the transform matrices anymore; it is the remaining scale-growth behavior through EvalMod / post-processing.
- `a_dsl_bts.sh` is useful for end-to-end generated-bootstrap testing on resnet20, but its current runtime failure is still downstream of primitive scale correctness.
- When matching rtlib bootstrap semantics, the most fragile spots are:
  1. the exact plaintext levels used by `Rotate_precomp(...)` for collapsed FFT
  2. the difference between “raise to max towers” and “raise to requested output level”
  3. honoring `level_after_bts` at the resnet callsite without cheating by delegating back to `Eval_bootstrap_ciph(...)`
- Static counting from generated source said `20` explicit bootstrap callsites, but the successful live run logged `21` executed bootstrap calls. Use the live count for wait-time estimates.
