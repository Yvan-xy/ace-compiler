## Takeaways

- `ace_edsl` is the active DSL and is AIR-first:
  - Python execution is traced directly into AIR via `ace_bindings`
  - `base_dsl` is reused mainly for AST preprocessing and surrounding infrastructure
  - `dsl_pybind11` should be ignored for new work
- The most important Python-side edit seams are:
  - DSL lifecycle and argument handling in `ace_edsl/edsl/edsl.py`
  - call-time decorator dispatch in `ace_edsl/edsl/domain_kernels.py`
  - operator semantics in `ace_edsl/edsl/core/air_value.py`
  - control-flow lowering in `ace_edsl/edsl/domain_ast_decorators.py`
  - pass orchestration in `ace_edsl/edsl/pipeline.py`
  - skip-op / Python lowering integration in `ace_edsl/edsl/lowering_registry.py`
- `ace_edsl` is not purely Python. New first-class ops or meaningful lowering work generally cross the seam into `ace_bindings` and the underlying C++ compiler libraries.
- `AceEDSL` uses a singleton plus call-time decorator lookup. This helps test isolation, but global state is still real and some tests explicitly clear the singleton.
- `AIRValue.FLAT_IR_MODE` is a core design choice:
  - operation results are stored to named temporaries and reloaded on demand
  - this keeps the traced AIR flatter and avoids nested-expression blowup
- A CKKS-specific front-end detail:
  - scalar/array Python values passed to `CkksPlaintext`-annotated params are encoded inside the kernel body
  - they are not formal AIR function parameters
  - array constants support complex-valued elements
- Control-flow support is currently asymmetric:
  - dynamic `if` can be represented in AIR
  - dynamic loop bounds are not fully implemented
  - non-unit loop steps fall back to Python execution
  - dynamic `while` predicates are not fully implemented
  - the FHE lowering path does not support all AIR control flow end-to-end
- The pipeline surface is split in two:
  - `AcePipeline` for programmatic compilation from an existing `GlobScope`
  - `Pipeline` for acepy-like fluent usage, especially ONNX loading and callback-driven lowering flows
- The ANT runtime bootstrap implementation is structured in three layers:
  - precompute/setup in `Bootstrap_setup`
  - key material preparation in `Bootstrap_keygen`
  - online evaluation in `Eval_bootstrap`
- The online bootstrap path is the expected CKKS structure:
  - modulus raising from level-0 data
  - `Coeffs_to_slots`
  - approximate modular reduction via Chebyshev plus double-angle iterations
  - `Slots_to_coeffs`
  - final scale / imaginary-part cleanup
- The runtime also exposes staged bootstrap entrypoints in `cipher.c` that mirror those phases for separate coeffs-to-slots, eval-mod, and slots-to-coeffs execution.
- There is a special low-budget path `(enc_budget == 1 && dec_budget == 1)` that routes through `Linear_transform`, but `Linear_transform()` in `bootstrap.c` is currently marked unimplemented.
- The DSL bootstrap example already contains the end-to-end C codegen entrypoint:
  - `ace_edsl/examples/bootstrap_full.py:run_demo()`
  - it traces the `@ckks_kernel` into AIR, runs `AcePipeline` from `fhe::ckks`, and writes `examples/output/bootstrap_full.c`
- `ACE_BOOTSTRAP_IMPL` controls what kind of bootstrap C gets generated:
  - `primitive` (default): decomposed DSL bootstrap stages
  - `rtlib`: direct CKKS bootstrap op intended to mirror the ANT runtime baseline
  - `evalmod`: legacy explicit EvalMod demo
- Host-side `ace_edsl` debugging depends first on environment readiness:
  - built `ace_bindings` shared modules
  - required Python deps such as `typing_extensions`
- For the native `a.sh` path, there were two distinct issues:
  - runtime abort from a missing external `.msg` file referenced by the generated `.inc`
  - link failure from a missing exported symbol in the installed rtlib archive
- The `encoder.c:562 invalid scaling factor for encode` regression was a compiler-side scale-management / lower-to-poly issue, not an rtlib encoder bug.
- The older `Rescale_ana` / `Handle_rescale` / `Rescale_expr` bundle from `rescale-fix.txt` was not sufficient by itself for the observed `resnet20` failure.
- Reinstating real down-scale lowering fixed the immediate regression signal:
  - generated C changed from `Init_ciph_down_scale(...)` count `0` to `188`
  - the previous early runtime scaling assertion no longer appeared in the same run path

## Lessons learned

- Default native compiler debugging to the `ace-compiler-dev` container; host-side failures are often environment mismatches.
- When a generated dataset executable fails at runtime, inspect `Get_rt_data_info()` in the generated `.inc` first to find the exact external data file path the runtime expects.
- When a symbol exists in source but not in the linked archive, check both:
  - stale installed archives under `/usr/local`
  - misplaced braces or similar source bugs that can accidentally create nested functions in GNU C
- For `ace_edsl`, decide early whether a change is:
  - Python-surface only
  - AIR-builder surface
  - full cross-seam work including bindings and downstream lowering
- Before debugging Python-side `ace_edsl` failures, verify both:
  - Python deps such as `typing_extensions`
  - built shared modules in `ace_bindings/`
- For active `ace_edsl` context, the most useful files to start from are:
  - `ace_edsl/docs/DESIGN.md`
  - `ace_edsl/edsl/edsl.py`
  - `ace_edsl/edsl/domain_kernels.py`
  - `ace_edsl/edsl/core/air_value.py`
  - `ace_edsl/edsl/domain_ast_decorators.py`
  - `ace_edsl/edsl/pipeline.py`
  - `ace_edsl/edsl/lowering_registry.py`
- The most relevant regression suites for ongoing DSL work are:
  - basic decorator/tracing tests
  - pipeline tests
  - selective lowering tests
  - bootstrap stage/full tests
  - vector/sihe control-flow tests for known backend gaps
- For scale regressions in generated CKKS C, a strong quick signal is the presence of `Init_ciph_down_scale(...)` sites rather than only counting `Rescale_ciph(...)`.
- For runtime bootstrap understanding, start from:
  - `fhe-cmplr/rtlib/ant/include/ckks/bootstrap.h`
  - `fhe-cmplr/rtlib/ant/ckks/src/bootstrap.c`
  - `fhe-cmplr/rtlib/ant/ckks/src/cipher.c`

  - compile-time macros in `bootstrap.h` such as `AUTO_SCALE`, `SPARSE_TERNARY`, `UNIFORM_TERNARY`
