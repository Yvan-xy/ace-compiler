## Takeaways

- `ace_edsl` is a repo-root Python package that traces Python execution directly into AIR through `ace_bindings`; it is not implemented as a wrapper around the deprecated `dsl_pybind11`.
- The implementation deliberately reuses only AST preprocessing and some infrastructure from `base_dsl`; MLIR generation is stubbed out and intentionally unused.
- The primary development seam is:
  - Python tracing/front-end in `ace_edsl/edsl/*`
  - C++ AIR/FHE lowering in `bindings/src/*` and the underlying `air-infra`, `nn-addon`, `fhe-cmplr` libraries
- `AceEDSL` uses a singleton DSL instance plus call-time decorator lookup. This simplifies test isolation, but global state is still a real concern and several tests explicitly clear the singleton.
- The pipeline surface is split in two:
  - `AcePipeline` for programmatic use with an existing `GlobScope`
  - `Pipeline` for acepy-like fluent use, especially ONNX loading plus skip-op / Python-lowering workflows
- Current sharp edges are explicit:
  - vector/FHE lowering does not yet support dynamic control-flow end-to-end
  - loop lowering only supports compile-time bounds and unit step
  - several AIRValue reverse/less-common operators remain unimplemented
- Build/runtime readiness for `ace_edsl` depends first on building shared pybind modules in `bindings/` and emitting them into `ace_bindings/`.

## Lessons learned

- For future `ace_edsl` work, start with these files first:
  - tracing and DSL lifecycle: `ace_edsl/edsl/edsl.py`
  - decorator/runtime entry: `ace_edsl/edsl/domain_kernels.py`
  - operator semantics: `ace_edsl/edsl/core/air_value.py`
  - control-flow lowering: `ace_edsl/edsl/domain_ast_decorators.py`
  - pass orchestration: `ace_edsl/edsl/pipeline.py`
  - selective lowering / skip-op bridge: `ace_edsl/edsl/lowering_registry.py`
- If a change touches ONNX import, Python lowering callbacks, or pass skipping, the shared binding layer is part of the same feature surface; do not treat `ace_edsl` as purely Python.
- The most relevant regression suites for active DSL work appear to be:
  - decorator/basic tracing tests
  - pipeline tests
  - bootstrap stage/full tests
  - selective lowering tests
  - vector/sihe control-flow tests for known backend gaps
- Before debugging Python-side failures, check whether `ace_bindings` has actually been built; missing `.so` files currently fail imports at module import time.

## Lessons learned

- When a generated dataset program fails with `Rt_data_open`, inspect `Get_rt_data_info()` in the generated `.inc` first; that reveals the exact external data file path the runtime expects.
- When a symbol appears in headers/source but not in the linked archive, check for:
  - stale installed archives under `/usr/local`
  - nested-function accidents in GNU C source caused by misplaced braces
- For this repo, native debugging should default to the `ace-compiler-dev` container; host-side `/app` failures are often just environment mismatches, not compiler bugs.
