# CPU RNS 并行探索：第三步正式对照结果

状态：第三步完成。结论：**保留旧策略；新的 NTT limb 模式保持实验开关。**

在同一份 runtime、相同 FHE 参数和 16 线程配置下，新 LimbParallel 的完整
BTS 中位耗时为 **28.618 秒**，比新 Serial 快 **12.5%**，但比旧策略慢
**23.4%**，CPU 时间也比旧策略高 **25.7%**。局部并行收益没有抵消关闭外层
双 EvalMod 分支并行的损失，本轮不将新模式设为默认。

## 1. 实验边界

- 三种模式：Legacy（预算 0，旧双分支策略）、Serial（预算 1，关闭双分支）、
  LimbParallel（NTT 预算 16，关闭双分支）。NTT worker 数受 OpenMP 预算限制。
- 主测分别使用 16 和 1 个 OpenMP 线程；每组一次预热、三次正式调用。
  16 线程依次测 Legacy/Serial/Limb，1 线程反向执行。
- 所有主测结束后，另测三种模式的 16 线程阶段诊断，每组同样预热一次、正式
  调用三次。共 9 组、**36 次完整 BTS**，其中 24 次为主测调用。
- 主测重新编译并链接，没有 NTT 计数包装函数、阶段 hooks 或 perf 采样。
  `getrusage` 快照在计时区间外，记录该次调用的 CPU/系统时间、缺页以及进程
  累计峰值 RSS；后者包含 setup、keys 和缓存常量，不是新增工作区大小。
- 所有执行顺序进行，采用同一隔离安装前缀，包含相同的统计竞争修复。
  Release `-O3 -DNDEBUG`、GCC/G++ 13.3、OpenMP，16-vCPU KVM 环境。
- `OMP_DYNAMIC=FALSE`、`OMP_PROC_BIND=close`、`OMP_PLACES=cores`、
  `OMP_MAX_ACTIVE_LEVELS=1`；恢复默认 allocator，清除额外 GOMP/allocator 调优
  和 LD_PRELOAD，不混入第二阶段探针或之前的 allocator 实验。
- 沿用 N=65536、32768 slots、degree=44、K=28、相同系数、Q=31/P=11、
  输入 Q=2、输出 Q=14、输入输出 scale=2^56 / scale degree=1 等原有参数。
  输出规范化在计时区间内，setup、加解密、输入复制和正确性检查在区间外。

Serial 与 Limb 的生成 C 经规范化比较，除线程预算和常量文件路径外完全一致。
本轮比较的是新旧 DSL，没有拿历史 OpenFHE 耗时计算新的 speedup。

## 2. 主结果：无诊断探针

单位：秒；样本列不包含预热。

| 线程数 | 模式 | 三次正式样本 | 中位数 |
| ---: | --- | --- | ---: |
| 16 | Legacy | 22.834530, 23.266957, 23.194996 | **23.194996** |
| 16 | Serial | 31.791064, 32.702238, 32.718497 | **32.702238** |
| 16 | LimbParallel | 28.976118, 28.195545, 28.618368 | **28.618368** |
| 1 | Legacy | 34.540250, 34.873787, 34.359983 | **34.540250** |
| 1 | Serial | 34.425893, 34.410754, 35.923278 | **34.425893** |
| 1 | LimbParallel | 34.236183, 34.629266, 34.362769 | **34.362769** |

1→16 线程的完整 BTS 加速比为：Legacy **1.49×**、Serial **1.05×**、
LimbParallel **1.20×**。单线程下三者相近，差异小于样本波动；没有据此宣称
新 Serial/Limb 单线程更快。

16 线程下，Limb 相对 Serial 少用约 4.084 秒，但仍比 Legacy 多用约
5.423 秒。两个差距都明显大于各自主测组内的耗时范围。

## 3. 资源成本

以下为 16 线程主测，CPU/系统时间和 minor faults 取正式调用中位数，RSS
取该进程运行的峰值。所有组的 major faults 均为 0。

| 模式 | CPU 秒/调用 | 系统 CPU 秒/调用 | minor faults/调用 | 峰值 RSS GiB |
| --- | ---: | ---: | ---: | ---: |
| Legacy | 60.597 | 6.393 | 964470 | 14.398 |
| Serial | 64.717 | 11.261 | 2168643 | 14.437 |
| LimbParallel | 76.197 | 8.301 | 1135653 | 14.440 |

Limb 相对 Serial 降低了墙钟时间，但增加约 17.7% 的 CPU 时间；相对 Legacy
既更慢又消耗更多 CPU。三组峰值内存接近，没有出现容量上的明显改善。
CPU 时间包含运行库开销和等待，不能将其直接解释为有效计算量；缺页差异也
不能仅凭这些数据归因于某一个函数。

## 4. 独立阶段诊断

单位：秒，各项为三次正式调用中位数。

| 阶段 | Legacy | Serial | LimbParallel |
| --- | ---: | ---: | ---: |
| CoeffToSlot | 9.078 | 8.848 | 9.014 |
| 共轭拆分 | 0.458 | 0.454 | 0.466 |
| **EvalMod** | **8.938** | **16.180** | **15.099** |
| SlotToCoeff | 5.425 | 5.339 | 5.375 |
| 诊断运行整次 BTS | 24.023 | 31.298 | 30.061 |

诊断中，Limb 的 EvalMod 比 Serial 少约 **1.081 秒（6.7%）**，说明所选
decomposition NTT 路径的调度在该阶段产生了局部净收益。但 Legacy EvalMod
仍快约 **6.160 秒**；其余主要阶段的诊断耗时相近。

阶段诊断是独立运行，插桩与运行时波动使其总时间与主测有所差异，因此不能
把该 1.081 秒当成主测 4.084 秒改善的精确分解，也不据此宣称单个 NTT 内核
的独立加速比。主排名和资源结论均采用上一节的无探针数据。

结果与第一步的覆盖分析一致：本轮只并行了 Decomp_modup 内的 NTT/INTT，
原 profile 中约占 EvalMod 用户态 CPU 样本的 18.13%。Mod_down、Rescale 的
NTT 和其它计算仍然串行；关闭旧双分支并行却影响了整个 EvalMod。
该占比是先前样本的覆盖证据，不是本轮的墙钟时间上界。

## 5. 正确性与验收结论

- 全部 **36 次调用通过** 32768 槽位的复数误差与 Q/scale 检查，最大误差
  为 **4.5095e-4**，低于共同门限 0.02。
- 每组样本编号、预热排除和资源记录数量均验证；阶段记录顺序及时间窗口
  连续性验证通过。三个主测二进制均检查不存在 NTT 包装函数和阶段 hook。
- 比较脚本通过编译检查，既有 4 个 benchmark 结果校验测试通过。未将本轮
  数据描述为新的并行正确性证明；相关逐系数/worker 检查见第二步报告。

验收问题的答案：

1. 所选路径是否有收益？**有局部证据**：相同串行分支安排下，Limb 的 EvalMod
   诊断和完整主测都优于新 Serial。
2. 是否抵消了关闭旧分支并行的损失？**没有。**
3. 能否替换旧策略？**当前不能。** 16 线程下完整 BTS 慢 23.4%，CPU 成本更高。
4. 是否继续扩大本轮范围？**不自动扩大。** 保持 `decomp_ntt_threads=0` 的
   默认值，保留实验实现与证据。若继续探索，应另行评估在保留分支并行的同时
   如何共享线程预算，或扩大热点覆盖；本轮不引入这些后续改动。

## 6. 复现与证据

```sh
python3 ace_edsl/benchmarks/cpu_bootstrap/compare_ntt.py \
  --ace-prefix tmp_cpu_ntt_step2/install --artifacts tmp_cpu_ntt_step2 \
  --threads 16 1 --repetitions 3
```

脚本校验第二步生成源和库的哈希，复用相同预编码常量，重新编译所有主测与
诊断二进制；因此不需要重新生成数 GiB 的常量文件。可用 `--skip-build`
复用经哈希校验的第三步二进制。

原始证据位于 `tmp_cpu_ntt_step3/`：

- `summary.json`：全部主测、资源和阶段结果。
- `{legacy,serial,limb}-t{16,1}.log`：无探针主测。
- `{legacy,serial,limb}-phases.log`：独立阶段诊断。
- `build.json`、`settings.json`、`cpu.txt`、`measurement-audit.json`：
  构建哈希、运行配置、CPU 信息及探针排除检查。

本轮仍是固定参数、确定性输入、每进程一组密钥和同一台虚拟机上的小规模
实验。结论足以决定该候选暂不替换默认策略，不推广为所有 CPU 或参数的结论。
